## 背景

当前项目的拼音候选主要依赖静态词典：

- 单字字典：`src/lib/dictionaries.ts`
- 高频词组：`src/lib/commonPhrases.ts`
- 常用姓名：`src/lib/commonNames.ts`
- 成语、地理、笔画等补充词典
- 候选排序主逻辑：`src/utils/pinyin.ts`

现状优点是稳定、可控、离线可用，但问题也很明显：

1. 静态扩词成本高，无法覆盖真实用户长期输入习惯
2. 候选排序无法根据用户个人偏好动态调整
3. 同一拼音在不同用户、不同业务场景中的优先级差异无法体现

因此，本次不继续扩充静态数据字典，而是引入“用户输入学习”能力：

- 记录用户实际选择过的拼音 -> 中文结果
- 用本地缓存做轻量学习
- 在不破坏现有离线词典兜底能力的前提下，动态提升更常用候选的排序

---

## 目标

实现一个默认开启、可关闭的“用户拼音输入学习”能力：

1. 封装 IndexedDB，缓存用户拼音输入与候选选择记录
2. 在设置面板中加入开关，默认开启
3. 在拼音联想阶段接入用户缓存数据，参与候选排序

---

## 非目标

本阶段暂不做：

1. 与本地拼音学习排序无直接关系的大范围能力扩展
2. 会显著增加实现复杂度、但不影响本阶段目标落地的输入法能力重构

本阶段的目标是“本地学习 + 候选排序增强”，不是完整输入法引擎升级。

---

## 后续扩展预留

虽然本阶段只做本地学习，但实现时需要为后续演进留空间：

1. 存储层要与业务逻辑解耦
   当前先落地 IndexedDB，后续如果增加云端同步，应能在不重写候选排序逻辑的前提下切换为“本地缓存 + 远端合并”
2. 学习数据结构要可扩展
   当前先保存 `pinyin / text / count / lastUsedAt`，后续应允许补充 `source`、`userId`、`deviceId`、`context` 等字段
3. 排序逻辑要可插拔
   当前先采用“静态词典 + 本地学习重排”，后续应允许插入更复杂的排序器，而不是把评分逻辑写死在拼音主流程里
4. 设置项命名要面向长期
   当前开关虽然只控制本地学习，但命名建议使用“拼音学习”而不是“IndexedDB 学习”，避免后续扩展到云端后语义不合适
5. 输入链路要预留异步增强能力
   当前采用“同步候选 + 异步重排”，后续如果要接入远端候选或模型服务，应能复用这一机制，而不是再次推翻

---

## 总体方案

整体分成 4 层：

1. `storage` 层
   负责 IndexedDB 的初始化、查询、写入、关闭、版本升级
2. `domain` 层
   负责用户拼音学习数据的结构定义、归一化、合并和排序评分
3. `hook / input` 层
   负责在用户选中候选时记录学习数据，在拼音联想时读取学习数据参与排序
4. `settings / UI` 层
   负责开关显示、持久化、说明文案、启用禁用逻辑

## 数据设计

### 1. 建议新增的本地数据库模块

建议新增：

- `src/utils/indexeddb.ts`
  纯 IndexedDB 基础封装
- `src/utils/pinyinLearning.ts`
  拼音学习领域逻辑

这样可以避免把浏览器存储细节直接塞进 `useInput.tsx` 或 `pinyin.ts`。

### 2. 建议的库配置

建议使用单独数据库：

- DB 名称：`rcVirtualKeyboardDB`
- Store 名称：`pinyinLearning`
- 版本号：`1`

### 3. 建议的记录结构

按“拼音 + 中文候选”维度存储：

```ts
type PinyinLearningRecord = {
  id: string; // `${normalizedPinyin}::${text}`
  pinyin: string; // 规范化后的拼音，如 nihao / ni'hao
  normalizedKey: string; // 去分隔符后的拼音，如 nihao
  text: string; // 用户最终选择的词，如 你好
  count: number; // 选择次数
  lastUsedAt: number; // 最后使用时间戳
  firstUsedAt: number; // 首次使用时间戳
};
```

### 4. 为什么不直接存整段输入历史

如果直接存完整输入日志，会带来这些问题：

1. 数据量增长过快
2. 查询排序成本高
3. 候选重排真正需要的是“拼音 -> 词”的统计权重，而不是全量原始日志

所以建议存聚合后的统计记录，而不是原始日志流。

## IndexedDB 封装计划

### 1. 基础能力

`src/utils/indexeddb.ts` 建议提供：

- `openVkbDatabase()`
- `getObjectStore(storeName, mode)`
- `idbGet(key)`
- `idbPut(value)`
- `idbBatchPut(values)`
- `idbGetAllByIndex(indexName, query)`
- `idbDelete(key)`
- `idbClear(storeName)`

### 2. Store 与索引设计

`pinyinLearning` store：

- 主键：`id`
- 索引：
  - `byPinyin` -> `pinyin`
  - `byNormalizedKey` -> `normalizedKey`
  - `byLastUsedAt` -> `lastUsedAt`

其中 `byNormalizedKey` 很关键，因为当前 `pinyin2ChineseV2` 会同时处理：

- `nihao`
- `ni'hao`
- `ni hao`

学习数据排序时，建议统一使用去分隔符后的 key 做主查询，再根据需要保留原始规范化拼音。

### 3. 容错策略

IndexedDB 不是 100% 可用，计划里必须考虑失败降级：

1. 打开数据库失败时，不影响输入流程
2. 读失败时，直接回退到静态字典排序
3. 写失败时，只打印 warning，不阻断用户输入
4. 在隐私模式或浏览器策略限制下，功能可自动退化为“无学习能力”

## 学习数据领域逻辑计划

### 1. 规范化规则

复用 `src/utils/pinyin.ts` 的输入规范化思路，保证学习数据和候选查询使用同一套规则：

- 转小写
- 去掉非字母、非分隔符
- 去掉多余空格
- 额外生成一个 `normalizedKey = 去掉分隔符后的拼音`

例如：

- `nihao` -> `pinyin = nihao`, `normalizedKey = nihao`
- `ni'hao` -> `pinyin = ni'hao`, `normalizedKey = nihao`
- `ni hao` -> `pinyin = ni hao`, `normalizedKey = nihao`

### 2. 建议提供的领域 API

`src/utils/pinyinLearning.ts` 建议提供：

- `normalizeLearningPinyin(input: string)`
- `recordPinyinSelection(pinyin: string, text: string)`
- `queryPinyinLearningCandidates(pinyin: string)`
- `sortCandidatesByLearning(baseCandidates: string[], learningRecords: PinyinLearningRecord[])`
- `clearPinyinLearningData()`

### 3. 排序策略

学习数据不应该替代静态词典，而应该“重排已有候选”并“少量补充历史词”。

建议排序权重分成两部分：

1. 频次权重
   `count` 越高，排序越靠前
2. 时间权重
   `lastUsedAt` 越近，排序越靠前

建议一个简单可控的评分：

```ts
score = count * 100 + recencyBonus
```

其中 `recencyBonus` 可以按最近 7 天、30 天、90 天分层。

### 4. 排序原则

建议遵循：

1. 用户历史精确命中的词优先
2. 静态高优词典仍保留兜底
3. 学习词只能提升，不应破坏输入稳定性到“完全乱序”
4. 最终返回数量仍受 `MAX_RESULT_COUNT` 限制

## 输入链路接入计划

### 1. 记录用户学习数据的触发时机

最佳接入点是 `useInput.tsx` 中真正“提交候选词”的位置。

当前关键路径：

- `updateChineseCandidates(value)` 负责生成拼音候选
- `onSelectChinese(chinese, appendText, options)` 负责候选回填
- `commitCurrentCandidate()` 也最终走 `onSelectChinese`

建议在 `onSelectChinese` 中增加记录逻辑：

只有满足以下条件时才记录：

1. 当前输入模式是 `ZH`
2. 当前存在 `inputValue`
3. 当前是拼音候选提交，而不是 OCR / 手写直接候选
4. 设置项“用户拼音学习”开启

### 2. 读取学习数据的接入点

建议在 `updateChineseCandidates(value)` 对应的候选生成阶段接入，而不是深入改写字典底层。

推荐方式：

1. 保持 `pinyin2ChineseV2` 继续负责基础候选生成
2. 在它返回结果后，再用用户学习数据做二次重排

这样风险最小，因为不会直接破坏现有静态词典算法。

建议改造成：

```ts
const base = onPinyin2Chinese(value)
const learned = await queryPinyinLearningCandidates(base.pinyin || value)
const sorted = sortCandidatesByLearning(base.chinese, learned)
```

### 3. 同步 / 异步问题

这里是本次方案的关键风险点。

当前 `onPinyin2Chinese` 是同步返回：

```ts
(value: string) => { pinyin: string; chinese: string[] }
```

而 IndexedDB 查询天然更适合异步。

所以计划里必须先做设计决策。

---

## 同步与异步设计决策

建议采用“两阶段候选更新”方案，而不是强行把整个 `useInput` 改成完全异步。

### 方案

1. 第一阶段
   先同步返回静态词典候选，保证输入体验即时
2. 第二阶段
   异步读取 IndexedDB 学习数据
3. 如果异步结果仍对应当前 `inputValue`
   再局部刷新候选顺序

### 优点

1. 不破坏现有同步输入体验
2. 不要求大规模改写 `onPinyin2Chinese` 类型
3. IndexedDB 慢时也不会阻塞输入

### 需要处理的问题

1. 用户快速连续输入时，异步返回结果可能过期
2. 必须比对当前 `inputValue`，只更新最新这一轮查询
3. 异步刷新候选时不要引起候选条闪烁太明显

### 建议实现方式

在 `useInput.tsx` 中增加一个查询序号或 request id：

- 每次拼音输入更新时递增
- 异步结果回来后，只有 request id 匹配当前值时才应用

## 候选排序策略细化

### 1. 基础规则

最终候选 = 静态候选 + 用户学习补强

排序建议：

1. 用户精确命中过的候选排最前
2. 静态高优词组仍保持高权重
3. 用户学到的词如果不在静态候选中，可少量插入前几位
4. 不允许无限扩张候选数量

### 2. 推荐排序步骤

1. 先生成静态候选 `baseCandidates`
2. 查询学习记录 `learningRecords`
3. 从学习记录里筛出与当前拼音匹配的词
4. 对学习词按 `count + recency` 评分
5. 合并为：
   - `learnedExactCandidates`
   - `baseCandidates`
   - `learnedExtraCandidates`
6. 去重并截断到 `MAX_RESULT_COUNT`

### 3. 为什么不完全交给学习词覆盖

如果完全让学习词覆盖静态排序，会有风险：

1. 少量误选会把候选顺序污染得太明显
2. 新用户冷启动时没有学习数据
3. 静态高频词组仍然是有效兜底

所以推荐“增强排序”，而不是“重写词典”。

## 数据清理与容量控制计划

虽然数据是本地存储，但仍建议提前加约束。

### 1. 单条记录自然聚合

同一 `pinyin + text` 只保留一条记录，通过 `count` 累加，不会无限增长。

### 2. 建议加上全库上限

例如：

- 最多保留 3000 条记录

超过时清理：

- 最久未使用
- 且使用次数低的记录

### 3. 后续可选能力

设置面板未来可以加：

- 清空拼音学习数据

但这不是本次必须项。

本次计划建议先预留 API，不一定首版就加按钮。

## 结论

这次需求最核心的不是“再加更多词”，而是把当前静态词典系统升级成：

- 静态词典兜底
- 本地输入学习增强
- 用户可控开关
- 可降级、可扩展、低侵入

推荐优先按“异步学习重排”的方向实施，而不是大幅重写 `pinyin2ChineseV2`，这样风险更小，也更适合当前项目结构。
